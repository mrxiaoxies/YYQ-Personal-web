# RAG + Wiki 优化设计

## 目标与范围

在现有主题聚合、混合检索和事实推导上增加持久化 Wiki 层，使个人项目概括、项目比较、技能与经历关系问题获得多证据回答。公开事实来自 knowledge/index.json；现有后台内容不自动成为个人经历证据。当前工作区已有 v0.4.2 和后台内容编辑改动，本功能应保留这些改动，不替换整文件，不自动提交或发布。

## 方案选择

推荐独立 Wiki 编译层，复用当前检索与回答服务。直接扩充 topic description 成本低，但缺少页面关系和逐项来源；接入完整 Microsoft VS Code 扩展会引入与网站运行无关的依赖。独立层可在 Netlify 打包，并保持原始 RAG 的安全门。

## 数据与编译

新增 knowledge/wiki/ 下的 Markdown 页面和机器可读 manifest。页面类型为个人、项目、技能、时间线；每个页面包含稳定 ID、标题、摘要、事实段落、sourceEntryIds、relatedPageIds、来源摘要和编译版本。只编译 public 条目，关系由明确来源映射产生，不能凭语义相似建立“使用过”关系。

首版生成器使用确定性来源抽取，保证可重复生成；可选 LLM 总结作为草稿，未通过来源审核不进入线上 manifest。明确区分这一版本的 Wiki 组织能力与未来 LLM 自动维护能力，不能把模板编译声称为 LLM 自动维护。

检查器验证来源存在且公开、链接目标存在、页面 ID 唯一和来源摘要一致。来源变化的页面视为过期，线上不能使用其总结，应回退原始检索。文件更新采用生成器输出，不在访客问答中写回知识库。

## 查询与回答

Wiki 搜索使用标题、别名、正文关键词与页面关系，返回少量相关页面；页面关系最多扩展一跳，有总数和上下文长度上限。先复用原始检索的具体能力和项目范围校验，再使用页面映射补充相关公开条目。Wiki 不得绕过未知技能、私有资料、项目隔离或 prompt injection 防护。

回答上下文区分“原始事实”“Wiki 综合说明”“服务端事实推导”。所有来源仍指向原始条目；Wiki 页只是组织层，不是独立证明。比较问题仅比较有公开资料支持的方面，不编造绩效、熟练程度或项目因果。没有学习日期时，项目日期不等于学习开始时间。既有就业跨度计算继续由 fact-derivation.ts 完成。

## 接入点

- 新增 Wiki 类型、校验器、编译脚本、生成产物、检索模块和测试。
- 在 ask-core.ts 组装上下文前接入 Wiki 证据解析，保持外部 ask 请求兼容。
- 向量索引首版保持原有 schema，Wiki 检索使用现有条目和主题向量辅助，不重复加载第二个模型。
- 更新知识维护文档、操作文档和变更记录；实现完成再核对版本号，避免覆盖已有 v0.4.2 改动。

## 验收

正例：个人项目总览、网站与微信助手共同点和差异、Linux 经验对应项目、测试技能在不同阶段的体现。负例：未知工具、跨项目借用 Codex、无证据的 RAG 学习日期、私有来源、过期页面、坏链接和恶意页面指令。比较回答需包含至少两组独立证据；失败时回退既有 RAG。运行现有测试、新增 Wiki 测试、真实混合评测、typecheck 和 build。验证结果只代表测试覆盖范围，不宣称所有自然问法均正确。

## 交付

交付本地实现、注释说明、生成和校验命令、修改路径和测试结果。非生产预览用于人工验收；本次不自动更新正式站。后续再增加受审核的 LLM 增量编译、矛盾检测和后台 Wiki 浏览界面。
