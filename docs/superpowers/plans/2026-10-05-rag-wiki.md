# RAG Wiki Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 为公开经历助手增加可追溯、可更新的 Wiki 组织层，改善综合和比较回答。

**Architecture:** 原始条目保持唯一事实来源。编译器生成 Markdown 和 JSON manifest；运行时校验新鲜度，以受限页面导航组织原始证据，复用现有混合检索、安全门和结构化回答。

**Tech Stack:** Node 24、TypeScript、JSON、Markdown、现有 BGE 与 Netlify Functions；不新增运行时依赖。

**Spec:** docs/superpowers/specs/2026-10-05-rag-wiki-design.md

## Global Constraints

- 只处理 public 来源；保留当前工作区 v0.4.2 和后台编辑改动。
- 访客问答不修改 Wiki；本次不自动更新正式站。
- 不把模板编译声称为 LLM 自动维护；可选 LLM 草稿不进入线上 manifest。
- Wiki 不绕过未知能力、项目隔离和原始来源校验。
- 注释说明操作目的；所有回答来源指向原始条目。

## Review Focus

- 原始条目删除或转私有后，旧 Wiki 必须失效。
- 一跳导航不能把其他项目工具变成当前项目经验。
- 比较问题只在两组证据均通过范围校验时综合。
- 页面正文的指令不得改变模型行为。
- 缺失学习日期时不从项目时间推断开始学习时间。

### Task 1: 编译与一致性校验

**Files:** 新增 netlify/functions/_shared/wiki-schema.ts、wiki-schema.test.ts、scripts/compile-wiki.mjs、knowledge/wiki/manifest.json 和 Markdown 页面。

**Interfaces:** WikiPage 包含 id、title、kind、summary、sourceEntryIds、relatedPageIds、sourceDigest；WikiManifest 包含 schemaVersion=1、knowledgeVersion、pages。validateWikiManifest(manifest, entries) 返回可用页面与失效原因。来源摘要使用 Node SHA-256 对公开条目的稳定字段序列计算。

- [ ] 写测试：公开来源可用；未知、私有、重复 ID、坏链接和摘要变化均失效。
- [ ] 运行 node --test netlify/functions/_shared/wiki-schema.test.ts，确认未实现时失败。
- [ ] 实现 schema、确定性编译器与知识编译命令。页面正文仅抽取源内容，链接由 topic.entryIds 和明确标签关系生成。
- [ ] 运行生成器两次，断言产物一致；校验模式发现失效或产物漂移时退出非零。
- [ ] 运行组件测试，记录结果，不提交混合工作区。

### Task 2: 受限 Wiki 检索与证据规划

**Files:** 新增 netlify/functions/_shared/wiki-retrieval.ts、wiki-retrieval.test.ts、wiki-data.ts。

**Interfaces:** planWikiEvidence(query, validatedPages, acceptedSourceIds) 返回最多 4 个页面、至多一跳链接和组织说明；仅返回来源均在 acceptedSourceIds 内的页面，不将未通过原始门控的条目变成事实。综合问题通过现有 retrieveKnowledge 对明确子问题独立检索，合并去重，最多 6 条；只有明确个人项目比较和技能到项目关系意图启用多查询。

- [ ] 写测试：网站与微信项目比较、Linux 对应项目、未知工具、养老金 Codex、过期页面、一跳总数和正文长度上限 6000 字。
- [ ] 运行测试确认失败后实现标题/别名/关键词匹配、受限导航和多证据规划。
- [ ] 对每个子问题复用传入 RetrieveKnowledge；未知具体工具仍拒答，比较缺一侧时不声称已完成比较。
- [ ] 运行组件和现有 retrieval、hybrid-retrieval 测试。

### Task 3: 回答集成与可追溯来源

**Files:** 修改 netlify/functions/_shared/ask-core.ts、ask-core.test.ts；必要时修改 netlify/functions/ask.ts 的模型上下文组装。

**Interfaces:** GroundedModelInput 保留原字段，新增可选 wikiContext；生产模型适配器将其作为组织说明传递。上下文中原始 evidence 仍是唯一事实依据。AskResponse 保持兼容，可选增加 Wiki 页标题诊断。

- [ ] 写集成测试：多项目结论使用实际两侧 sourceEntryIds；Wiki 指令无效；无学习日期仍不得生成日期证据；普通单项目问法结果不变。
- [ ] 运行测试确认失败，再接入证据规划和 Wiki 上下文。明确提醒模型综合说明不构成新事实。
- [ ] 校验最终来源来自实际结论支持的原始条目，比较时可展示最多 6 条来源，避免只展示第一侧。
- [ ] 运行 ask-core、ask、health 测试与 typecheck。

### Task 4: 评测、版本与交付

**Files:** 修改 scripts/evaluate-hybrid-retrieval.mjs、scripts/verify-rag.mjs、package.json、package-lock.json、VERSION、CHANGELOG.md、knowledge/README.md、docs/OPERATIONS.md。

- [ ] 加入 Wiki 综合、比较、日期缺失与跨项目反例，分别断言检索接受、来源和拒答。
- [ ] 增加 wiki:build、wiki:check 命令；构建前执行只读一致性检查。
- [ ] 核对现有 v0.4.2 改动后设置独立下一版本，保留其他变更记录。
- [ ] 运行 npm test、npm run evaluate:rag、npm run typecheck、npm run build；检查差异和生成产物。
- [ ] 交付修改路径、命令用途和实测结果。非生产部署复用已授权的 yyq-web Draft 流程；若账户不可用，保留本地产物并报告真实限制。

## 执行方式

推荐由当前助手顺序实施：四项任务依赖同一数据与回答接口，避免并行修改共享文件。实施前需要审阅本计划；不自动创建提交、推送或正式部署。
